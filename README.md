## 1. Executive Summary & Intent

Traditional academic and certification examinations suffer from systemic centralized vulnerabilities:
- **Pre-Exam Paper Leaks:** Compromised administrator accounts or centralized database leaks release exam questions before test day.
- **Post-Submission Answer Tampering:** Malicious or compromised database administrators can alter submitted student records undetected.
- **Opaque & Biased Grading:** Subjective grading is inconsistent, lacks accountability, and leaves students with no auditable proof of evaluation fairness.

**Open-XP** solves these challenges through a **hybrid zero-trust architecture** uniting **Solana's immutable trust layer** with **AWS's enterprise scale and generative AI**.

## 2. Core Architectural Pillars

<img width="3060" height="1904" alt="image" src="https://github.com/user-attachments/assets/08dc54d9-99ee-4128-a4b2-af7f2c4d3975" />


### Pillar 1: The "Zero-Leak" Guarantee (AWS KMS + Solana Multisig)
* Question papers are envelope-encrypted using a unique Data Key generated by **AWS KMS (AES-256-GCM)** and stored in **Amazon S3**.
* The KMS decryption key is **cryptographically locked**. The `/exam/key` Lambda queries the Solana blockchain Devnet; unless the `ExamState` PDA has reached its appointed multisig threshold (e.g. 3-of-5 examiner approvals) and flipped `is_live == true`, KMS decryption is denied.
* Once unlocked, decryption happens **strictly in-memory** in the student's browser via the **Web Crypto API (`window.crypto.subtle`)**—never writing plaintext to server or client storage.

### Pillar 2: Anti-Tamper Submission Receipts (DynamoDB + Solana PDAs)
* When a student submits answers, the backend stores the submission in **Amazon DynamoDB** and computes an exact **deterministic SHA-256 hash**.
* The student immediately signs a Solana transaction calling `submit_answer_hash`.
* This logs the hash permanently under the student's `AnswerRecord` Program Derived Address (PDA). Even if a malicious database administrator alters answers in DynamoDB, the altered record's hash will no longer match the on-chain receipt.

### Pillar 3: Verifiable & Transparent AI Grading (Amazon Bedrock + Step Functions)
* When the examination window closes, an **AWS Step Functions** pipeline triggers automated grading.
* **Amazon Bedrock (Anthropic Claude 3.5 Sonnet)** evaluates subjective responses via the **Converse API** with a strict tool specification (`toolSpec.strict: true`).
* Bedrock outputs guaranteed structured fields: `score` (0-100), `rubric_match`, and `justification`.
* An `EvaluationHash` (SHA-256 hash of the grade and justification) is anchored directly to the student's `AnswerRecord` on Solana via `record_evaluation`.

## 4. End-to-End Workflow

### Phase A: Exam Creation & Encryption (Pre-Exam)
1. Exam Admin logs into `/exam/create` with their authority Solana wallet.
2. The admin uploads questions, defines the examiner public keys, and specifies the multisig threshold (e.g., 2-of-3).
3. The `/exam/create` Lambda calls AWS KMS `GenerateDataKey` (`KeySpec: AES_256`).
4. The paper is encrypted in-memory using AES-256-GCM. The encrypted payload is uploaded to S3 (`exams/${examId}/paper.enc.json`).
5. The admin's wallet signs the Solana `initialize_exam` transaction, persisting the `s3_uri`, `multisig_threshold`, and `is_live: false` in the `ExamState` PDA.

### Phase B: Multisig Decryption & Exam Unlock
1. Authorized examiners log into the `/dashboard` with their wallets.
2. Examiners review the exam details and click **"Approve as Examiner"**, sending an `approve_exam` transaction to Solana.
3. Once the multisig threshold is satisfied, the contract transitions `is_live = true`.
4. A student clicks **"Fetch KMS Key & Decrypt Paper"** on `/exam/[id]`.
5. The `/exam/key` Lambda queries Solana Devnet, verifies `is_live == true`, invokes KMS `DecryptCommand` on the stored ciphertext blob, and returns the plaintext key.
6. The student's browser decrypts the paper in-memory via the Web Crypto API.

### Phase C: Exam Execution & Tamper-Proof Commitment
1. The student answers the subjective questions.
2. Clicking **"Submit to DynamoDB & Sign On-Chain"** sends the answers to `/exam/submit`.
3. The Lambda saves the answers to DynamoDB and returns a deterministic SHA-256 hash.
4. The frontend prompts the student's wallet to sign `submit_answer_hash(answer_hash)`.
5. The Anchor program permanently records this hash on-chain inside the student's `AnswerRecord` PDA.

### Phase D: AI Grading Pipeline & On-Chain Anchoring
1. AWS Step Functions triggers `EvaluateExamFunction`.
2. The Lambda reads student answers from DynamoDB.
3. Bedrock Claude 3.5 Sonnet evaluates the answers via the Converse API with strict `toolSpec` demanding `score`, `rubric_match`, and `justification`.
4. The Lambda updates DynamoDB with the evaluation and computes `EvaluationHash` = `SHA-256(evaluation)`.
5. The backend grading wallet signs `record_evaluation`, permanently anchoring the grade and `EvaluationHash` to the student's `AnswerRecord` PDA on Solana.

## 6. Local Setup & Build Guide

### Prerequisites
- Node.js >= 20.x and `pnpm >= 9.0.0`
- Rust toolchain (`rustc`, `cargo`)
- Solana CLI (`solana-cli >= 1.18`)
- Anchor CLI (`anchor-cli >= 0.30`)
- AWS CLI & AWS SAM CLI (optional for live AWS deployment)

### Installation
```bash
# Clone the repository
git clone https://github.com/your-org/open-xp.git
cd open-xp

# Install dependencies across all workspaces
pnpm install
```

### Build Everything
```bash
# 1. Build the shared schemas, types & IDL
pnpm --filter @repo/shared build

# 2. Build the AWS SAM Lambda handlers
pnpm --filter api build

# 3. Build the Next.js frontend
pnpm --filter web build

# 4. Verify the Solana smart contract (Rust)
cargo check --manifest-path apps/programs/programs/open-xp/Cargo.toml
```

### Running Locally
```bash
# Run the Next.js frontend dev server
pnpm --filter web dev
# Open http://localhost:3000 in your browser
```

### Deploying Smart Contracts to Solana Devnet
```bash
cd apps/programs
anchor build
anchor deploy --provider.cluster devnet
```

### Deploying AWS Serverless Backend
```bash
cd apps/api
pnpm build
sam build
sam deploy --guided
```

## 7. Security & Compliance Notes

1. **Non-Custodial:** Private keys never leave user wallets; backend wallets only anchor evaluation attestations.
2. **Deterministic Cryptography:** All payload hashes sort object keys prior to serialization, ensuring bit-for-bit SHA-256 reproducibility across client and cloud.
3. **Zero In-Transit Plaintext Leakage:** Raw question papers reside encrypted in S3, undergo KMS authorization checks, and decrypt in ephemeral browser RAM.
